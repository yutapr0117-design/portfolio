# 盲点の探し方 —— どの次元をまだ測っていないか

**54 件の不利な事実のうち、後半に出たものほど「次元そのものが未検査」だった。**
個々の発見より、**どうやって見つかったか**のほうが再利用できる。この文書は
「次に何を探すか」ではなく「**次にどの測り方を使うか**」を残す。





## 入口ページに、自分で作った短い扉が載っていなかった（2026-09-09）

**#116 の disposition で「長さへの実際に効く緩和は短い入口である」と書いた。**
書いた直後に、その短い入口が**入口ページに載っていない**ことが分かった。

同じ日に作った `ACD-1.0.objection-map.md`（1 表・638 語）は
`LICENSES/README.md`（GitHub がディレクトリで自動描画する日本語の索引）からは辿れたが、
**`REVIEWERS.md`（審査者向けの英語の入口）には無かった。**
**リストから来る読者が着地するのは後者である。**

**同じ節でもう 1 つ出た** —— 見出しが *"The three things you probably want first"* で、
**表は 8 行**あった。**見出しに数を書くと、行を足した瞬間に合わなくなる。**
この文書群の既定は**数えずに列挙する**であり、そこだけ外れていた。

**一般形（#58 と同じ）**: **最後に書かれ、最初に読まれるページが、いちばん監査されない。**
新しい成果物を作ったら、**それが最初に読まれる場所から辿れるか**を同じ増分で確かめる ——
索引に足すのと、入口に足すのは別の作業である。


## 自分が今日書いたものを、同じレンズで読み返す（2026-09-09）

**26 増分・3,478 行を足した日の終わりに、その日の追加分だけを対象に走査した** ——
絶対量化子・enforcement 主張・「初めて」の主張。**2 件出た。**

**(1) 行番号を根拠に引いていた。** `index.html:403` が 2 か所（`reviewer-positions.md` と
`AS-OF.md`）。**その時点では正しかった**（実測で 403 行目）。だが**行番号は黙って動く値**であり、
**審査者を存在しない行へ送る**。`grep -n 'rel="license"' index.html` に置き換えた ——
**§4c の様式（コマンド → 結果）がこの文書群の既定であり、そこだけ様式から外れていた。**

**まだ Check にしない。** 実例は 1 件で、このリポジトリの規律は
**「per-instance で複数回潰してから構造防止へ昇華する」**である。**再発したら Check にする**
（`LICENSES/*.md` で `<file>.<ext>:<行番号>` を禁じるだけなので実装は軽い）。

**(2) 「初めて測った」の裏を取った。** 2026-09-09 に「ACD-1.0 の語数を一度も測っていなかった」
と書いた。`git log -S` で確かめると**その主張は正しい**が、**2026-09-06 に「100 語あたりの否定語数」
を測っている** —— つまり**語数は中間値として既に計算されており、審査者が使う単位として
表に出されていなかっただけ**である。**「測れなかった」ではなく「測ったのに書かなかった」。**
この区別は主張を弱めるのではなく強くする。

**この掃引を毎回やる必要はない。** 効いたのは**その日に大量に書いた日**だけである。


## 検出器が「46 件の壊れた強制主張」を報告しかけた（2026-09-09）

**「我々が引く `Check <識別子>` は、ツールの出力に実在するか」**を測った。AST で
`check(...)` 呼び出しの文字列だけから識別子を集め、追跡下の `.md` の引用と突き合わせた。
**結果は「530 件中 46 件が解決しない」。**

**そのまま報告していれば、重大な誤報だった。**

**実際に起きていたのは別のこと** —— 出力の `OK:` 行 **746 本のうち 144 本は、自分の Check 番号を
名乗っていない**。低番号の Check（1〜36 など）は説明文だけを出す。**つまり 46 件の大半は
「壊れた強制主張」ではなく「自分に名前を付けない Check」である。**

**残った真の欠陥は 3 つだけで、いずれも面の記号に関するもの**だった ——
441 / 445 / 451 は面の letter を出力に載せるのに、**444 / 142 / 7 は載せない**。
その結果 `LICENSES/` が「**Check 444a が BLOCKING で強制する**」と書いても、
**第三者はその識別子を出力の中に見つけられなかった。**

**修正は 2 つ**: 444 の OK メッセージに 7 面の記号を載せた／142 の OK メッセージが
**自分が要求している 3 つ目の path（この workflow 自身）を述べていなかった**のを直した ——
**強制している内容より小さく自己申告する Check**は、過大申告と同じくらい出力を信用できなくする。

**そして「Check にしない」判断も残す。** 「引用した識別子はすべて出力に現れること」を
機械強制すると、**144 本のメッセージを名乗らせるためだけに書き換える**ことになる。
得られるのは grep 可能性だけで、**名前の権威は `check-repository-consistency-map.md` にある**。
費用が便益を上回る。

**教訓は 3 度目のもの**（#111 / #114 / #115 と同じ族）: **集合の一部を測って集合について結論した。**
ここでは検出器が「引用側」だけを疑い、**出力側の慣行がそもそも一様でない**ことを見ていなかった。
**数を報告する前に、その数を作った道具の前提を書き出す。**


## 面を列挙してから確かめる（2026-09-09・3 度の同型失敗のあとに固定した）

**2026-09-09 に、同じ形の失敗を 3 度した。**

| 何を確かめたか | 何に一般化したか | 記録 |
|---|---|---|
| その**文**を grep して 0 件 | **論点**が新しい | #111 |
| **条文**を読んで整合 | **文書**が整合している | #114 |
| 1 文の**後半**を読んで errata 化 | その**文**を読んだ | #115 |

**共通形: 集合の 1 つを確かめて、集合について結論した。**

**対処は「気をつける」ではなく、確かめる前に集合を列挙すること。**
ACD-1.0 について何かを主張するとき、その主張が及ぶ面は **5 つ**である ——
**PREAMBLE / §16.1 の推奨 notice / `machine.json` の `notice` / 適用宣言 `LICENSE` /
提出文 §B.0**。条文だけではない。

**この 5 面については、絶対量化子（no / all / every / nothing / only / without …）を含む文を
2026-09-09 に全部読んだ。** 結果は #115 に記録した（2 面に欠陥・1 面は非 operative と自己申告・
2 面は正確で、うち 1 面は修正の手本になる）。**この掃引は済んでいる。**

**次に同じレンズを当てるなら、面ではなく主語を変える** —— たとえば
「**リポジトリ**について述べた文」（README / STATUS / AIO 層）や
「**手続き**について述べた文」（REVISION-PROTOCOL / READY-TO-SUBMIT）である。
**面の一覧はここに書いてあるので、同じ 5 面を数え直すのは新しい増分ではない。**


## 中心にある観察

> **盲点は「まだ探していない場所」ではなく「まだ使っていない測り方」に在る。**

同じ次元で掘り続けると収穫は逓減する。実際、条文の敵対的読解は 4 巡目から
「既に答えてある」が増えた。一方、**次元を変えると 1 回目から出る** ——
言語の次元（#53）とリンク構造の次元（#54）は、どちらも**最初の測定で欠陥を出した**。

理由は単純で、**その次元を測る検査が 1 つも無かった**からである。内容を読む検査を
何百回走らせても、ファイルが何語で書かれているかは分からない。

## 自分で作った検査が自分を壊す形（2026-09-05 に 2 例目を踏んだ）

**新しい gate を入れるときの失敗 class として、独立に記録する。**

> **その gate を満たす操作が、gate 自身を破らないか。**

**踏んだ 2 例**:

| いつ | 何が起きたか |
|---|---|
| 2026-08-23 | 行数を数える実装が `splitlines()` と `wc -l` で 1 行ずれ、**Check 52 の警告値と Check 424 の照合値が食い違って CI が赤**になった。正しく通っていた値を「直した」ことで壊れた |
| 2026-09-05 | 新設した Check 461b が「frontmatter の日付 ≥ git の最終更新日」を BLOCKING で要求 —— **日付を直す commit 自身がその git 日付を進める**ので満たしえず、さらに一括変更が**内容を触っていない文書の git 日付まで進める**。CI が落ちた |

**共通する構造**: 検査対象が「**編集すると値が動く**」もの（行数・日付・digest・件数）である
とき、**修正という行為そのものが新しい違反を生む**。この class は**ローカルでは出にくい** ——
作業ツリーがその一括変更を経ていないと、条件が偶然満たされてしまう。

**入れる前に問うこと**:

1. この gate を**満たす操作**を書き下せるか。その操作は gate を破らないか。
2. 対象と**無関係な変更**（footer の追加、フォーマット、一括置換）で値が動くか。動くなら
   BLOCKING にしない。
3. **許容差**が必要か。厳密一致を要求できるのは、値が編集と独立なとき（digest など、
   対象そのものを固定しているとき）だけ。
4. 最初の非 vacuity 検証を**ローカルだけで済ませていないか**。461b は 1 度目が
   import 欠落で**何も検査せず成功を報告**し、2 度目は**CI でしか落ちなかった**。

**この 2 例はどちらも「盲点を潰すために作った仕組み」が原因である。** 検査を増やすことは
それ自体がリスクを増やす行為でもある、と記録しておく。

**他の Check に同じ構造が無いかは掃引した（2026-09-05）。** BLOCKING かつ「編集で動く値」を
厳密一致で見る Check を機械的に洗い、候補は **Check 236 の 1 件**だった。読んだところ
`aio-manifest.json` の `generated_at` を検査するが、**見ているのは書式（ISO 形式か）であって
git 日付との一致ではない** —— 同じ構造ではない（clean）。

行数を見る Check 424 / 363 / 365 は「編集で動く値」を扱うが、**`wc -l` を単一の権威に統一
してある**ので、値の定義が実装間でずれない限り破れない。2026-08-23 の事故はまさにその
「定義がずれた」ケースで、統一はその是正である。**つまりこの class への既存の答えは
「値の定義を 1 つにする」であり、461b はそれができない対象（git 日付は編集の副作用で動く）
に厳密一致を要求したのが誤りだった。**

> **⚠ 2026-09-13 追記 —— この文書が持っている「使った次元」の表にも、同じ罠がある。**
> 表の各行は **「いつ、何に当てたか」**を書くが、**「その次元がまだ当たっていない対象」は書かない。**
> 本日 2 回、**使用済みの次元を新しい対象へ当てただけで実欠陥が出た**

> E16 の追記 = 定義語の次元 → 1.1 草案）。

## crash は grep をすり抜ける（2026-09-06・Check 463 で 2 度踏んだ）

非 vacuity の実証は「mutation を当てて RED を見る」だが、**その RED をどう読むかで結論が反転する**。

Check 463 の検証で、私は 2 度とも「**発火しなかった**」と読んだ。実際には:

  - 1 度目 —— 新 Check が他の Check の分岐内で定義される局所名（`_L460`）を借りており、
    **`UnboundLocalError` で suite ごと停止**していた

    検出したうえで crash**していた

**出力を絞って読むと、crash は「何も起きなかった」に見える。**

**規律**: 非 vacuity は「ERROR が出たか」ではなく「**意図した Check が意図したメッセージで
落ちたか**」で見る。絞り込む前に**終了コードと全出力**を確認する。そして新しい Check には
**自分の list と自分の `check()`** を持たせる —— 他の Check の局所名を借りると、順序が変わった
瞬間に「働かない」ではなく「**suite を止める**」形で壊れる —— **止まった Check は一度も走っておらず、以降の Check も全部 masking される**という、このリポジトリが以前に一度踏んだ形と同じである。

**同じ検証で 3 つ目も踏んだ**: 手で当てる mutation の **first-occurrence 置換**は、同じ文字列が
別節にもあると**別の場所を打つ**。`Proposed Tags:` は §A.0 と §B.0 の両方にあり、素朴な置換は
§A.0 を打っていた。**対象範囲を切り出してから置換し、occurrence が減ったことを確認してから**
走らせる。
