# 盲点の探し方 —— どの次元をまだ測っていないか

**54 件の不利な事実のうち、後半に出たものほど「次元そのものが未検査」だった。**
個々の発見より、**どうやって見つかったか**のほうが再利用できる。この文書は
「次に何を探すか」ではなく「**次にどの測り方を使うか**」を残す。

## 中心にある観察

> **盲点は「まだ探していない場所」ではなく「まだ使っていない測り方」に在る。**

同じ次元で掘り続けると収穫は逓減する。実際、条文の敵対的読解は 4 巡目から
「既に答えてある」が増えた。一方、**次元を変えると 1 回目から出る** ——
言語の次元（#53）とリンク構造の次元（#54）は、どちらも**最初の測定で欠陥を出した**。

理由は単純で、**その次元を測る検査が 1 つも無かった**からである。内容を読む検査を
何百回走らせても、ファイルが何語で書かれているかは分からない。

## 外から来た材料は、事実ではなく測り方として受け取る（2026-09-05・初めて実地で検証された）

本文書はこれを予測として書いていた —— 「**外から次元を示唆されたときが最も価値が高く、具体的な
欠陥ではなく次元の名前で受け取る**」。2026-09-05 に実際にそれが起き、予測どおりに動いた。

届いたのは、OSI で審査中の別 instrument（OpenMDW / ModelGo）のレビューに参加している側からの
観測で、**場所も答えも指定されなかった**。渡されたのは (a) hosted-only 配信では notice 義務が
発生しないという提出者の解釈と、それが 2025-03 に「mere use への条件になり得る」として notice
要件を削除した経緯と整合するという説明、(b) litigation termination がどこで open-source
principle を越えるのかを分解する問い、の 2 つ。

**事実としての新規性はゼロだった。** どちらも前日（2026-09-04）にアーカイブを直接読んで #46 /
#47 として還元済みで、同じ材料から同じ結論に達していた。

**測り方としての新規性が 2 つあった。** (a) は「具体的な配信経路を 1 つ置き、義務が発火するまで
追う」という手順で、(b) は「争点を境界候補へ分解してから可否を言う」という手順。前者を*本文
そのものの再頒布形態*へ横滑りさせると #56 が出た。後者を*条件の射程*へ当て、定義語を使う側の
節から追うと #57 が出た。

**どちらの次元も、この文書の候補リストには無い。** それは欠落ではなく、末尾の「この文書自身の
限界」が述べていることの実例である —— **列挙できる次元は既に使った次元**であり、候補リストは
原理的に網羅になりえない。

**手渡され方が結果を決めた。** 具体的な欠陥を教えられていたら、それを直して終わっていた。
次元の名前ですらなく「材料」として受け取ったので、**どの次元へ翻訳するかを自分で決める工程**が
残り、収穫はそこで起きた。これは礼儀の問題ではなく手順の問題で、次に外から何かが来たときも
同じ形で受けること —— **答えを先に聞かない。**

## 自分で作った検査が自分を壊す形（2026-09-05 に 2 例目を踏んだ）

**新しい gate を入れるときの失敗 class として、独立に記録する。**

> **その gate を満たす操作が、gate 自身を破らないか。**

**踏んだ 2 例**:

| いつ | 何が起きたか |
|---|---|
| 2026-08-23 | 行数を数える実装が `splitlines()` と `wc -l` で 1 行ずれ、**Check 52 の警告値と Check 424 の照合値が食い違って CI が赤**になった。正しく通っていた値を「直した」ことで壊れた |
| 2026-09-05 | 新設した Check 461b が「frontmatter の日付 ≥ git の最終更新日」を BLOCKING で要求 —— **日付を直す commit 自身がその git 日付を進める**ので満たしえず、さらに一括変更が**内容を触っていない文書の git 日付まで進める**。CI が落ちた |

**共通する構造**: 検査対象が「**編集すると値が動く**」もの（行数・日付・digest・件数）である
とき、**修正という行為そのものが新しい違反を生む**。この class は**ローカルでは出にくい** ——
作業ツリーがその一括変更を経ていないと、条件が偶然満たされてしまう。

**入れる前に問うこと**:

1. この gate を**満たす操作**を書き下せるか。その操作は gate を破らないか。
2. 対象と**無関係な変更**（footer の追加、フォーマット、一括置換）で値が動くか。動くなら
   BLOCKING にしない。
3. **許容差**が必要か。厳密一致を要求できるのは、値が編集と独立なとき（digest など、
   対象そのものを固定しているとき）だけ。
4. 最初の非 vacuity 検証を**ローカルだけで済ませていないか**。461b は 1 度目が
   import 欠落で**何も検査せず成功を報告**し、2 度目は**CI でしか落ちなかった**。

**この 2 例はどちらも「盲点を潰すために作った仕組み」が原因である。** 検査を増やすことは
それ自体がリスクを増やす行為でもある、と記録しておく。

**他の Check に同じ構造が無いかは掃引した（2026-09-05）。** BLOCKING かつ「編集で動く値」を
厳密一致で見る Check を機械的に洗い、候補は **Check 236 の 1 件**だった。読んだところ
`aio-manifest.json` の `generated_at` を検査するが、**見ているのは書式（ISO 形式か）であって
git 日付との一致ではない** —— 同じ構造ではない（clean）。

行数を見る Check 424 / 363 / 365 は「編集で動く値」を扱うが、**`wc -l` を単一の権威に統一
してある**ので、値の定義が実装間でずれない限り破れない。2026-08-23 の事故はまさにその
「定義がずれた」ケースで、統一はその是正である。**つまりこの class への既存の答えは
「値の定義を 1 つにする」であり、461b はそれができない対象（git 日付は編集の副作用で動く）
に厳密一致を要求したのが誤りだった。**

## まだ使っていない測り方（候補・優先順位なし）

**思いついた順に書く。優先順位を付けると、付けた根拠のほうが先に古くなる。**

- **外部リンクの生死** —— アーカイブ URL が将来も解決するか
- **図表の有無** —— 表で示すべきものを散文で書いている箇所（逆も）
- **機械可読層との一致** —— `machine.json` の各主張が散文の主張と食い違わないか

**2026-09-05 に候補リストを 5 件消費した。** 残りは 3 件（外部リンクの生死 / 図表の有無 /
機械可読層との一致は使用済み）。**消費が速いこと自体は問題ではない** —— この文書の主張は
「候補リストは網羅になりえない」なので、**リストが尽きることと次元が尽きることは別**である。
実際この日に出た 4 つの次元（再頒布の形態・定義語の射程・読む順序・想定読者の網羅）のうち、
**候補リストに載っていたのは 2 つだけ**だった。

## crash は grep をすり抜ける（2026-09-06・Check 463 で 2 度踏んだ）

非 vacuity の実証は「mutation を当てて RED を見る」だが、**その RED をどう読むかで結論が反転する**。

Check 463 の検証で、私は 2 度とも「**発火しなかった**」と読んだ。実際には:

  - 1 度目 —— 新 Check が他の Check の分岐内で定義される局所名（`_L460`）を借りており、
    **`UnboundLocalError` で suite ごと停止**していた
  - 2 度目 —— 直したあとも別の局所名（`_bad460`）へ append しており、**marker の欠落を正しく
    検出したうえで crash**していた

**どちらも私の `grep -E "^ERROR"` に掛からなかった。** traceback は `ERROR:` で始まらないからである。
**出力を絞って読むと、crash は「何も起きなかった」に見える。**

**規律**: 非 vacuity は「ERROR が出たか」ではなく「**意図した Check が意図したメッセージで
落ちたか**」で見る。絞り込む前に**終了コードと全出力**を確認する。そして新しい Check には
**自分の list と自分の `check()`** を持たせる —— 他の Check の局所名を借りると、順序が変わった
瞬間に「働かない」ではなく「**suite を止める**」形で壊れる —— **止まった Check は一度も走っておらず、以降の Check も全部 masking される**という、このリポジトリが以前に一度踏んだ形と同じである。

**同じ検証で 3 つ目も踏んだ**: 手で当てる mutation の **first-occurrence 置換**は、同じ文字列が
別節にもあると**別の場所を打つ**。`Proposed Tags:` は §A.0 と §B.0 の両方にあり、素朴な置換は
§A.0 を打っていた。**対象範囲を切り出してから置換し、occurrence が減ったことを確認してから**
走らせる。

## 「次の未採掘」リストも stale になる（2026-09-05 に実測）

候補リストが網羅になりえないのと同じことが、**その逆側のリスト**でも起きる。CLAUDE.md §7 は
「次の未採掘」を 3 件挙げていたが、実測すると **2 件は既に採掘済み**だった —— OSD 逐条は
#1〜#10 すべて提出パケットにあり、名指しされていた §5.2 の反 DRM 条項は **4 箇所**で論じられ、
`license-review` の追加要件は「満たしていない 3 件を先に書く」形で記録済みだった。

**害は「重複して書く」ことではなく「次のセッションが再導出に 1 サイクル使う」こと。** 引き継ぎ層は
それを無くすために在るので、そこに古い to-do があるのは目的の逆を向いている。

**規律**: 「次の未採掘」を書くときは、**その場で 1 回 grep して既出でないことを確かめる**。
確かめずに書いた項目は、書いた瞬間から「まだ無いことの主張」になり、他の自己申告と同じく
**書いた当日に古くなりうる**（Check 460 が件数について強制しているのと同じ性質だが、
こちらは意味の判断なので機械化できない —— だから規律として書く）。

## 「動く数」と「書いた時点で誤り」は別の失敗（2026-09-06 に 3 件で確定）

自己申告の検査はずっと**動く数**（一覧が伸びる / 日付が進む）を追ってきた。同日に見つかった
3 件は**どれも動いていない**:

  - `submission.md` §4c の clause pointer「29 / 29」（実体 33。入力は凍結された記述子）
  - 同 §4c の定義語 最小「Contribution at 4」（実体 3・同値の語あり。入力は凍結本文）
  - `comparison.md` §1.35「six / remaining two」（実体 4 + 3 = 7。**宣言と列挙が同じ commit**）

**再確認では原理的に見つからない。** 再確認は「前と変わったか」を見るので、最初から誤って
いるものは何度確認しても同じ値を返す。見つける唯一の方法は**成果物から導出し直す**ことで、
face (i)/(j) はそう作った。**この区別は、次に「数字は確認済み」と言いたくなったときに効く。**

## 誰も、自分に同意している部分は読み返さない（2026-09-06）

不利な事実の一覧は entry 単位で維持されていたのに、**唯一の擁護節（`against.md` の
"What survives"）は 3 点が古かった** —— clause pointer 29（実体 33）/「6 つのうち 4 つ・残り 2 つ」
（実体 7 のうち 4・残り 3）/「errata 5 件・不利な事実 45 件」（実体 10 / 69）。

**非対称の理由は単純である。** 反論は書くたびに読み返され、擁護は書いたら終わる。
外から来た審査者は両方を並べて読むので、**擁護が古く反論が正確な文書は「我々が実際に確認して
いるのはどちらか」を見せてしまう**。

**いちばん悪かったのは数字ではない。** その節は自分の件数を述べたうえで
「**Check 460 now enforces them**」と書いていた —— enforce していなかった。
**偽の enforcement 主張は stale な数字より悪い。読み手に「確かめなくてよい」と伝えるからである。**

**規律**: 自己申告の掃引をするとき、**不利な側だけでなく擁護している側も同じ回で当てる**。
そして「この数は Check が守っている」と書くときは、**その Check を開いて確かめてから書く**。

### なぜ「引用した Check の実在」を Check にしなかったか

**掃引は 12 件すべて clean で、機械化も容易である**（番号を集めて突き合わせるだけ）。それでも
足さなかった理由は 2 つある。

1. **失敗モードが実質存在しない。** Check 番号は追記のみで、削除すると Check 45（連番の
   bijection）が即座に落ちる。つまり「引用先が消える」経路は別の BLOCKING が先に塞いでいる。
2. **今回の実害（#70）は番号を持っていなかった。** 壊れていたのは
   「**この数は Check 460 が守っている**」という文で、**番号は正しく実在していた**。
   番号を追う検査は、この形に原理的に届かない。**守れるものと、守りたかったものが違う。**

**代わりに規律を書いた**（同ファイル上部）——「この数は Check が守っている」と書くときは、
**その Check を開いて確かめてから書く**。機械化できないので、そう書く。

## 「自分の状態について書いた文は、いま真か」は 1 つの族である（2026-09-06 に 6 形）

2026-09-06 に出た #63〜#73 は、別々の発見に見えて**同じ問いの言い換え**だった。形が 6 つある:

| 形 | 例 | 腐り方 |
|---|---|---|
| **件数** | 「All 14 adverse facts」 | 一覧が伸びると古くなる |
| **面ごとの開示** | 送る文面に来歴が無い | 別の場所に在るので気付かない |
| **配信** | 公開バイト列と pin の照合 | repo が緑でも公開面だけ動く |
| **期限切れの条件** | 「未送信なら §5 に足す」 | 条件は**書いた瞬間に一度だけ**評価される |
| **不在の主張** | 「CI では強制していない」 | 機構を足しても**散文を探しに行かない** |
| **enforcement の被覆** | 「Check 460 が守っている」 | 番号は実在するのに**その面を覆っていない** |

**共通する構造**: どれも「書いた時点では真だった」か「書いた時点で確かめなかった」かのどちらかで、
**書いた本人が再読しない場所**ほど長く残る。だから**掃引は主張の種類ごとに機械化し、内容ごとに
やらない** —— 内容で追うと、読んだところしか直らない（#71 がその実例）。

**そして是正は一方向に偏らない。** 過大を直すと過小になる（#73: 「強制している」→「強制して
いない」、どちらも偽）。**是正するときは、前の文ではなく機構そのものを読む。**

## この文書自身の限界

**候補リストは、私が思いつける次元しか含まない。** 「まだ使っていない測り方」を
網羅的に列挙することは原理的にできない —— **列挙できるならそれは既に使った次元である**。

だから**この一覧が尽きても、盲点が尽きたことにはならない**。#52 で記録したとおり、
「発見がゼロ」は「その日のレンズでは出なかった」以上を意味しない。

**外から新しい次元を示唆されたときは、それが最も価値が高い** —— 自分の中から出ない
からこそ盲点なのであって、#53 と #54 はどちらも外からの示唆で始まった。示唆は
**具体的な欠陥ではなく次元の名前**で受け取るのがよい。欠陥を教えられると、それを直して
終わってしまう。
