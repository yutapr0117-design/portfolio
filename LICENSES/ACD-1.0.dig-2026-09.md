# 93 か月の掘削と、そこで検定した仮説（2026-09-17）

**`ACD-1.0.review-corpus.md` から切り出した**（985 行で advisory を鳴らしたため・
**節番号は動かしていない**ので既存の `§1.91` / `§1.93` 参照はここへ解決する）。

**corpus との境界**: corpus は**件数の census**（全期間を数えて参照クラスの大きさを出す）。
**ここは仮説の検定** ——「長さ / 新参 / 個人であること / 問いの重さ が、返信の有無を説明するか」。
**census は『どれだけ在るか』を、検定は『なぜそうなったか』を扱う。**

## 1.91 `license-discuss` を 2019-01〜2026-09（93 か月・2,420 通・299 スレッド）で掘り直した —— そして「長すぎたから返信が無い」は、我々の測り方の誤りだった（2026-09-17）

**掘った理由**: オーナーが 2026-09-17 に短い版を送るにあたり、「**8 月の投稿が長すぎた結果、議論が進まない**」
という読みを前提にしていた。**その前提を測ったら、崩れた。**

### 🔴 最大の発見 —— 8 月の投稿は、受信箱では 867 語だった

**アーカイブの当該ブロックを構造で読むと**、本文は署名まで **867 語**で終わり、そこから
`-------------- next part --------------` が **2 回**現れる ——1 回目は **HTML 版のスクラブ告知**、
2 回目が **添付された `ACD-1.0.txt` を pipermail が展開したもの**である。
**本文自身が *"The complete license text is attached as ACD-1.0.txt."* と述べており、実際に添付だった。**

**つまり 5,778 語（我々が「delivered」と呼んできた数）は、アーカイブの見え方であって受信箱の見え方ではない。**

**我々の道具が「delivered = 受け手の inbox に届いた本文全体」と定義していたのが誤り**で、
`measure_list_verbosity.py` は `next part` の後ろを本文として数えていた（訂正済み。
`inbox` / `attached` / `delivered` の 3 つに分けた）。

**この誤りは判断に効いていた** ——「8 月が長すぎた」は B3（長さ）の最も身近な証拠として使われていた。

**⚠ 逆側（同じ段落で書く）**: **アーカイブは公開記録であり、そこを読む人は 5,808 語に出会う。**
**添付という形式そのものを嫌う審査者もいる**（URL を好む）。そして **B3 の本体は無傷である** ——
委員長が engage しなかった 2 例（3,888 語 / 約 4,500 語）は**ライセンス本文の長さ**についてであって、
送り状の長さについてではない。**崩れたのは「8 月の*メール*が長すぎた」だけである。**

### 測定 1 —— 長さは、返信が付くかを予測しない

事務連絡・ダイジェストを除いた **299 スレッド**で、**最初のメッセージの語数**別に返信率を測った。

| 本文（散文）語数 | n | 返信あり | 割合 |
| :-- | --: | --: | --: |
| <200 | 157 | 109 | **69.4%** |
| 200–499 | 96 | 76 | **79.2%** |
| 500–999 | 36 | 26 | **72.2%** |
| ≥1000 | 10 | 7 | **70.0%** |

**アーカイブ上の展開量（引用・添付込み）で測っても同じ**（<300: 72.9% / 300–999: 72.3% /
1000–2999: 71.4% / ≥3000: **3 件すべて返信あり**）。**最長は 7,862 語（Project Tick・返信 8）。**

**したがって `license-discuss` では、長さは返信の有無をほとんど説明しない。**

### 測定 2 —— 初投稿者の方が、返信をもらっている

| 開始者 | n | 返信あり | 割合 |
| :-- | --: | --: | --: |
| **その人の初出スレッド** | 146 | 118 | **80.8%** |
| 常連 | 153 | 100 | 65.4% |

**「新参は無視される」は、この窓では成り立たない。**

### 測定 3 —— 沈黙がいつ情報になるか

返信が付いたスレッド（n=223）の**初回返信までの時間**: **中央値 8.1 時間**、
**24 時間以内 70.9% / 48 時間以内 85.7% / 1 週間以内 94.2%**（最大 3,437 時間）。
スレッド全体の **29.1% は最後まで返信ゼロ**。

**導かれる読み**: **1 週間沈黙したスレッドが、その後に返信を得る確率はおよそ 1 割**
（≈13 / 106）。**「まだ来ていない」と「来ない」の境目は、だいたい 1 週間である。**

### 測定 4 —— ライセンスを持ち込んだスレッド（n=28・8 年分）

**21 件（75.0%）に返信が付いた。返信ゼロは 7 件で、その内訳が重要である。**

| 日付 | 語数 | 件名（抜粋） |

| 2020-01-04 | 40 | [License-review] AGPL timeline & why cautious processes |
| 2020-12-13 | 36 | [License-review] GDPR compliance through software licence |
| 2022-12-14 | 39 | [License-review] Final comment on Open Logistics Licen… |

| **2026-08-26** | **867** | **Discussion Request: ACD-1.0** |
| **2026-09-06** | **835** | **Discussion Request: ACD-1.0 — one threshold question** |

**5 件は 4〜66 語の短い連絡・クロスポストであって、議論を求めた投稿ではない。**
**実質的にライセンスの議論を求めて返信がゼロだったのは、この 8 年で我々の 2 通だけである。**

**⚠ 何を establish しないか**: **理由は分からない。** 主題・時期・書き手・偶然のどれも排除できず、
**「substantive な提示で返信ゼロ」の n は 2 で、しかも 2 件とも同じ書き手である** ——
**「我々の投稿」と「この書き手」を分離できない。** 長さ・新参・時間帯では説明がつかない、
という**除外**までが、この測定の到達点である。

### 方法（再現できるように）

`https://lists.opensource.org/pipermail/license-discuss_lists.opensource.org/<YYYY>-<Month>.txt` を
ブラウザ相当の UA で取得（93 か月）。**encoded-word を復号してから**件名で正規化（`Re:` と
リスト接頭辞を剥がす）→ スレッド化。**事務連絡（`digest, vol` / `summary` 等）を除外**しないと、
返信ゼロの月次ダイジェストが長文バケットを汚染する（**初版はこれで「1000–1999 語は 41.7%」という
誤った谷を出した**）。

## 1.93 オーナーが挙げた 4 つの仮説を、掘ったコーパスに当てた（2026-09-17）—— 2 つは支持され、2 つは否定された

**2026-09-17、オーナーが沈黙の理由として 4 つ挙げた。**「測れる問いに散文で答えない」という
`REVIEWERS.md` の *check us* に従って、**4 つとも当てた。**

### (a)「前の 2 通は本文を読まないと答えられない形。今回は『何でも良いから意見を』だから反応が来やすい」→ **解像しなかった**

最初のメッセージ本文（8,000 字まで）を型で分けて返信率を測った:

| 型 | n | 返信あり |
| :-- | --: | --: |
| 条項を名指しして問う | 24 | 79.2% |
| どちらでもない | 275 | 73.1% |
| 広く意見を求める | 6 | 66.7% |

**方向はむしろ逆に見えるが、「広く意見を求める」は n=6 で、差は解像しない。**
**支持も否定もできない、が正しい答えである。** ただし ——**「条項を名指しして問う」形が
返信を減らしてはいない**ことは言える（79.2%）。**前の 2 通が「重い形だったから」返信が無かった、
という説明は、この窓では支えられない。**

### (b)「ディスカッションの方はそもそもやり取りの数が少ない」→ **支持される（ただし最近だけ）**

| 年 | `license-discuss` | `license-review` |
| --: | --: | --: |
| 2019 | **88.7 通/月** | 62.5 通/月 |
| 2023 | 7.9 | 13.1 |
| 2024 | 17.2 | 13.7 |
| 2025 | 15.1 | **29.4** |
| 2026（9 か月）| 11.4 | **33.7** |

**2025 以降、`license-review` は `license-discuss` の 2〜3 倍の流量を持つ。**
**ただし歴史的には逆で、2019 年の discuss は月 88.7 通あった** ——
**「discuss は元々静かな場所」ではなく、「discuss が静かになった」が正しい。**

### (c)「本申請と異なり、レビューする必要性が低い」→ **部分的に否定される**

**スレッドが立ったあとの挙動は、2 つのリストでほとんど変わらない**（2023 年以降）:

| | スレッド数 | 返信が付いた割合 | 1 スレッドあたり返信数 |
| :-- | --: | --: | --: |
| `license-discuss` | 86 | **79.1%** | 4.1 |
| `license-review` | 132 | **81.1%** | 5.0 |

**違うのは会話の数であって、会話する意欲ではない。**
**79% が返信を得る場所で、実質的な提示が 2 回連続でゼロなのは、やはり普通ではない。**

### (d)「申請者は企業単位、私は一個人」→ **否定される**

**フリーメール（＝個人）から始まったスレッドの方が、返信率が高い**（299 スレッド）:

| 開始者のアドレス | n | 返信あり |
| :-- | --: | --: |
| **フリーメール（gmail / icloud / proton / 163 等）** | 75 | **84.0%** |
| それ以外のドメイン | 224 | 69.2% |

**ライセンスを持ち込んだ個人は、軒並み返信を得ている**（`nik.sharky at gmail.com` の AI-MIT に 10 通 /
`lemonhub.io at icloud.com` の AGPL 議論に 11 通 / `amogusforever at protonmail.com` の
「新しいライセンスの出し方を教えて」に 5 通 / `anandchowdhary at gmail.com` の Twente License に 12 通 /
`van.lindberg at gmail.com` の CAL に 25 通）。

**⚠ 逆側**: 「それ以外のドメイン」は企業とは限らない（`cowan at ccil.org` / `tg at mirbsd.de` は個人ドメイン）。
そして**返信ゼロだった組織アドレス 4 件はすべて委員長の手続き連絡**であって、意見を求めた投稿ではない。
**つまりこの表が否定しているのは「個人だから無視される」であって、「企業だと有利」ではない。**

### 4 つを当てた結果として残るもの

**長さ・新参・個人であること・問いの重さ**は、**どれも我々の沈黙を説明しない。**
`license-discuss` の流量が落ちたことは事実だが、**それは「スレッドが少ない」ことであって
「立ったスレッドが無視される」ことではない。**

**説明が付かないという結果そのものが、今わかっていることである。**
**n=2 で書き手も同じなので、「この投稿」と「この書き手」を分離できない** ——
**次の 1 通が、その分離に使える唯一の実験になる。**

## 1.94 (d) の検定はやり直した —— 測っていたのは「後ろ盾」ではなく「メールのドメイン」だった（2026-09-17・オーナー指摘）

**§1.93 (d) は「申請者は企業単位、私は一個人」を*メールアドレスのドメイン*で測り、「否定される」と書いた。**
**オーナーの指摘で、それが問いとずれていたと分かった** ——
**「めちゃくちゃ大きい組織に所属している 1 個人」と「後ろ盾が無い単なる 1 個人」は違う。**

**ドメインはその区別を捉えない。** `van.lindberg at gmail.com` は gmail だが、書き手は
このリストで最も知られた弁護士の 1 人である。**つまり §1.93 (d) が否定したのは
「フリーメールだから無視される」であって、オーナーが述べた命題ではなかった。**

### 測り直し —— 「そのリストで知られているか」を、事前投稿数で代理する

**後ろ盾そのものは測れない**（所属を機械的に判定できない）。**測れるのは「このリストに
それまで何通書いていたか」**で、これは *立場* ではなく *馴染み* の代理指標である。
ライセンスを持ち込んだ 33 スレッドについて、開始時点での事前投稿数で分けた:

| 開始者の事前投稿数 | n | 返信あり | 返信数の中央値 | 返信者数の中央値 |
| :-- | --: | --: | --: | --: |
| **0 通（冷たく到着）** | 16 | **15（94%）** | **6** | **3** |
| 1–9 通 | 5 | 4（80%） | — | — |
| 10 通以上（常連） | 12 | 7（58%） | 2 | 2 |

**冷たく到着した方が、返信率も返信の量も多い。** 常連側の返信ゼロ 5 件は、
**すべて委員長らの手続き連絡**（クロスポスト・最終コメント）であって意見を求めた投稿ではない。

### したがって

**オーナーの精緻化した命題も、この窓では支持されない。** ただし **§1.93 (d) の書き方は
過大だった**ので、**判定を「否定される」から次のように置き換える**:

> **「後ろ盾の有無」は測れていない。測れた代理指標（このリストでの事前投稿数、
> および所属を示さないアドレス）では、後ろ盾が見えない個人が返信を得ている。**

**⚠ 逆側（同じ段落で）**: **返信の*量*は小さいものもある**（1 通が 2 件）。
**「返信が来るか」と「議論になるか」は別の問い**で、後者は後ろ盾で変わりうる ——
CAL（Van Lindberg・Holochain）は 25 通、CERN OHL は 2 通である。**この表が否定しているのは
「後ろ盾が無いと無視される」であって、「後ろ盾は関係ない」ではない。**

## 1.95 OSAID の checklist を原典で読み、承認済み 141 本を走査した —— gap が OSI 自身の表で裏づく（2026-09-17）

**きっかけはオーナーが共有した 2026 年 10 月の OSI 関連イベント**（とくに **10/20 All Things Open の
OSI「State of the Source」track** と **10/21 Opening Convening for Open Source AI（OSI × Duke・
OSAID の実装が議題）**）。**OSAID 本体は 2026-09-06 に読み済み**（`review-responses-meta.md` Q32d）だが、
**checklist は読んでいなかった。**

### OSI の checklist は、要素ごとに「license」と「terms」を書き分けている

| 要素 | 求められるもの |
| :-- | :-- |
| Datasets / Research paper / Technical report / Data card | **OSI-approved terms** |
| Code（前処理・訓練/検証/テスト・推論・支援ライブラリ）| **OSI-approved license** |
| **Model architecture** | **OSI-approved license** |
| **Model parameters** | **OSI-approved terms** |

**そして checklist は "terms" を脚注で定義している**:

> *"**Available under OSI-approved terms** means that the OSI will review licenses **and agreements**
> to ensure that all materials are available under terms that conform with the Open Source Definition."*

**つまり "terms" は「何でもよい」ではなく「OSI が OSD 適合を審査する」**である。
**Q32d が意図的に解かないまま残した非対称に、OSI 自身の定義が付いた。**

**そして `license-review` の参加者が、同じ読みを公開の場でしている**（2026-09-14・OpenMDW スレッド）:
*"it is quite clear that the OSI contemplates that things other than OSI-approved licenses might be
suitable for **model parameters**, but **that does not apply to code or model architecture materials**."*
（逐語は `rounds/2026-09-14-license-review-openmdw-thread-observed.txt`）

### 承認済みライセンス 141 本を走査した —— 該当語はほぼ皆無だった

**SPDX の license-list-data から `isOsiApproved` かつ非 deprecated の 141 本の本文を取得**して数えた
（2026-09-17）:

| 語 | 該当数 / 141 |
| :-- | --: |
| **"sui generis"** | **0** |
| "database" | 3（`WordNet` は対象物の名前・`PostgreSQL` は製品名・`OLFL-1.3` は「データベースで使ってよい」の許諾文脈）|
| "text and data mining" / "data mining" | **0** |
| "machine learning" / "training" | **0** |

**対照（検出器が効くことの確認）**: **`CC-BY-4.0` では "sui generis" が検出される**ので、
**0 は検出器の欠陥ではない。** なお **CC0-1.0 は OSI 承認集合に入っていない**（審査中に撤回された）
ので、この 0 は「データベース権に触れる instrument が存在しない」ではなく
**「OSI が承認した 141 本の中に無い」**である。

### ACD にとっての含意（狭く書く）

**OSAID の checklist が "OSI-approved terms" を要求するのは、コード以外の成果物**である ——
**データセット・データカード・技術報告・研究論文・モデルパラメータ**。
**ACD-1.1 はそれらを射程に持つ**: §1.3 の *Work* が *"source code, object code, documentation,
**data, metadata**, audiovisual material, and any collection or compilation of these"* を含み、
**§7 が sui generis database 権を Covered Right として扱い**、§6 が Computational Use を明示的に許し、
§8.4 の特許許諾が**モデル・パラメータ・出力**に届く。

**つまり「既存で埋まらない gap」（OSI の承認基準 7・要件である）に、OSI 自身の表と実測が付いた。**

### ⚠ 逆側 —— この節が establish しないこと

1. **OSAID 適合は承認の条件ではない**（理事会が明言・`board-decisions.md`）。**この節は承認の理由にならない。**
2. **OSAID は parameters について *"They may be free by their nature"* とも述べる** ——
   **パラメータに権利が及ばないなら instrument は要らない**、という読みが同じ文の中にある。
   **我々の §9 が解く問題は、存在しないかもしれない。**
3. **語が無いことは、効果が無いことではない。** MIT や 0BSD は "sui generis" と書かずに
   *"deal in the Software without restriction"* と書く ——**広い文言が黙示に及ぶ**という読みは成り立つ。
   **測ったのは*明示*の有無であって、*効果*の有無ではない。**
   **⚠ 2026-09-18 追記 —— この読みは実際に狭まった。** grant 条項を逐語で当てると、
   **`CAL-1.0` §3.1(a) は *"non-patent intellectual property laws of any jurisdiction"* に及び、
   database 権にも届く**（`comparison.md` §1.96）。**したがって「承認済みに database 権へ届くものは無い」は偽**であり、
   **正しくは「条件ゼロで届くものが無い」**である。**この節の 0 という数字は変わらないが、そこから引ける結論は変わった。**
4. **ACD は承認されていない**ので、**今日この slot を埋められない。** これは循環であり、
   **「承認が要る理由」にはなっても「承認すべき理由」にはならない**（Q32d が既に述べた線引き）。
