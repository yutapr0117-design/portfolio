## 何をもって「達した」としたか

**レンズを変えて読み、その日の発見がゼロになるまで繰り返した。** 2026-08-24 の発見数の推移:

```
自分が同日に追加した条項の欠陥      4 件   （§11.4 の §12 との矛盾 / §8.4 の「確認」形 /
                                        §8.2 の射程 / §4.5 の逆読み）
構造の欠落                        2 件   （§8 が licence 1 本 → §8.6 / 倒産・管財 → §2.9）
内部矛盾                          1 件   （§15.8 が前提にする翻訳を §16.4 が禁じていた → §16.5）
見出しと内容のずれ                 2 件   （§8 / §4）
最終の通し読み                     0 件   ← ここで判断した
```

**⚠ この「0 件」は 2026-08-24 時点の値であり、以後の発見によって明確に反証された（2026-09-05 追記）。**
凍結後の敵対的読解で **120 件の不利な事実**と **13 件の errata**（うち §16.1 は本文が読み手に
誤った行動を指示している）が出ている。**当時の判断が誤りだったのではなく、判断の根拠に
した「ゼロ」の意味が狭すぎた** —— あれは「その日に使ったレンズでは新しい発見が出なかった」
であって、「もう欠陥は無い」ではない。

**この区別を書き落としていたことこそが、ここに記録すべき欠陥である。** 「発見がゼロに
なるまで繰り返した」という文は、**打ち止めを主張しているように読める**。第三者が本書と
`ACD-1.0.against.md` を並べれば、前者が後者に反証されている形になり、**readiness の判断
そのものが疑われる**。

正しい言い方は「**その日に用意できたレンズを使い切った**」である。レンズは後から増える ——
実際、凍結後に増えたレンズ（他 instrument の実審査 / オーナー自身のレビュー投稿 /
語彙の計量 / 自己言及的主張の機械検証 / 時間軸）が、上の 5 つでは出なかったものを出した。

**提出の判断基準としては、それでよかったのかどうか。** よかった、と考えている ——
提出は「欠陥がゼロであること」を条件にすべきではなく、そうすると永久に出せない。
条件は「**知っている欠陥を隠していないこと**」であり、それは当時も今も満たしている。
ただし**その基準を明示せずに「ゼロ」とだけ書いたのは、基準の掏り替えに見える。**

使ったレンズと結果は `acd-license-rationale.md` §5.2 に一覧がある（審査員 / 採用者 /
敵対的承継人 / 翻訳者 / 被告側弁護士 / 機械 / SPDX 法務 / 見出し / 通し読み（順・逆））。

## 残る弱点（隠さない）

1. **法的レビューを受けていない。** 弁護士の確認を経ていない。とくに §12（人格権）は日本法の
   学説状況に依存する。提出パケットの「Honest disclosures」節でこれを**先に自分から述べて**いる。
2. **実使用が薄い。** 本リポジトリ 1 件のみ。SPDX は「相当程度の実使用」を求める。
3. **dedication 型への委員会の慎重論。** CC0 の経緯があるので、形式そのものが論点になりうる。
   §2.4 / §4.4 / §4.6 と見出し（§3 / §4 / §5 が同じ権利への 3 footing）がこれへの直接の対処。

4. **先例が 6 年間くり返されていない（2026-09-06 に実測）。** 公開トラッカー 252 件をこの類型で
   検索すると、承認は **The Unlicense（2020・legacy 基準＝我々が使えない経路）の 1 件のみ**で、
   同時代の試みは **1 件・未決着**である（`against.md` #87）。

**最も来そうな最初の反応は「弁護士を入れなさい」である。** 実際、我々の 19 日前に同型を出した
提出者は、リスト上で **McCoy Smith 氏から「approvable なものを出したいなら弁護士の助けが要る
だろう。IP 権の放棄は国際法制も絡んで複雑で、独力では機能するものにならない」**と言われている
（2026-08-07）。**これは論破すべき反論ではない** —— 我々の弱点 1 そのものであり、答えは
「その通りで、我々にはそれが無い」である。**代わりに述べられるのは、弁護士の代替にならないと
断ったうえでの機械的検証**（提出パケット §4c）だけである。**代替だと主張しないこと。**

**1 と 2 は起草では解消できない。** これ以上テキストを磨いても動かないので、
「レビュー結果を得る」段階へ進む判断をした。3 はまさにレビューで答えが出る論点である。

## 実際に行われたこと（2026-08-26 時点）

**OSI `license-discuss` へ投稿済み・結果待ち**（2026-08-26 オーナー明確化）。

`license-discuss` は OSI の**一般的な議論リスト**であり、**承認申請の窓口ではない**。
承認申請の窓口は `license-review` で、そこへはまだ出していない。SPDX License List にも
出していない。つまり現時点で提出したのは「**意見を聞く**」ことだけであり、
**承認の手続きはまだ何も始めていない**。

下の「人間が行うこと」§4 と `ACD-1.0.submission.md` §B は license-review 宛の文面だが、
それは**将来の手順**であって、送ったものではない。

**そして「将来」の対象は、凍結中の 1.0 ではない（2026-09-09・オーナー直接確認）。**
最初からの計画は **`license-discuss` → 外部指摘を収集 → 十分に取り込んだ改訂版を作る →
その改訂版を `license-review` へ提出**であり、**本申請後も 1 回で終える計画ではない** ——
レビューで出た指摘を次版へ反映し、必要なら改訂と再提出を繰り返す。
**したがって §B.0 は「1.0 を送る文面」ではなく「改訂版を送るときの雛形」である。**
ここに書かれた要求項目・開示・比較の枠組みは版が変わっても使えるが、
**版数・gap の記述・既知欠陥の一覧は改訂版のものへ差し替える。**

**SPDX を見送ったのは意図的である。** SPDX は「相当程度の実使用」を求めるが、現在の使用実績は
本リポジトリ 1 件で、その条件を満たしていない。**満たしていないものを出さない**という判断で
あって、順序の都合ではない。上の「残る弱点」2 と同じ事実を、提出側の行動として反映した形。

レビューで受けるであろう指摘への想定問答は `LICENSES/ACD-1.0.review-responses.md` にある
（弱点を先に自分から述べる 4 項目・OSD 逐条・条項別の想定問答・1.1 で直す候補）。

**本文は凍結中。** 妥当な指摘を受けたときの正しい返答は「ACD-1.1 でこう直す」であり、
審査中の差し替えではない（審査側が見ているテキストとの乖離を作らないため）。

## 人間が行うこと

`LICENSES/ACD-1.0.submission.md` §D のチェックリストに従う。要点だけ:

1. **送るのは `submission.md` §B.0（約 600 語）である。§B.1 以降を貼らない。**
   §B.1 は「送る文面の背後にある参考資料」であり、リストは code of conduct で
   **簡潔かつ低 volume** を求めている（`REVISION-PROTOCOL.md` §3.7）。
   **§B.0 は OSI が求める 10 項目をすべて含んでおり、Check 463 がその存在を BLOCKING で守る。**
2. **本文を plain text で添付する。** OSI の process は「attachment in simple text format」を
   求めており、2026-07 の実例では審査者の最初の返信が
   「**動的に変わらない版が評価には要る**」だった。添付が公開コピーと同一であることは
   `grep -E "^[0-9a-f]{64}  " LICENSES/FROZEN.md | shasum -a 256 -c` で審査者自身が確かめられる。
   **この形は 2026-08-26 の `license-discuss` 投稿で既に取れている**（2026-09-07 にアーカイブの
   MIME 構造を実測: text/plain の送り状 + その text/html 代替 + **本文を載せた第 2 の text/plain
   パート**。送り状の 2 つの代替は語単位で一致し、本文はそれとは別のパートに在る）。
   **アーカイブから確かめられないのは 1 点だけ** —— そのパートが filename を持っていたか、
   すなわち受信側が「添付ファイル」として見たか「続きの本文」として見たか。オーナーは
   送信控えで確かめられる。**確かめたうえで、次の提出でも同じ形を取る。**
3. `npm run verify` が exit 0 であることを確認（XML と本文の同期、宣言面の整合が証明される）
4. **パケット中の URL がすべて解決することを確認する**（同じ 2026-07 の実例で、審査者の
   別の返信が「**your links are broken**」だった。`REVISION-PROTOCOL.md` ゲート 7b）
5. **テキストは既に凍結されている**（2026-08-24〜・`LICENSES/FROZEN.md` の存在が凍結を意味し、
   Check 453 が 3 file の sha256 を pin する）。**提出時にすることは凍結ではなく、凍結を解かない
   こと**である。以後の改善は `ACD-1.1` / `ACD-2.0` という別識別子で行い、`ACD-1.0` が指す
   テキストは動かさない（§16.4 が条文としてもこれを定めている）
6. **（未実施）** OSI の**承認申請**は `license-review@opensource.org`（**購読してから投稿**）/
   SPDX は https://tools.spdx.org/app/submit_new_license/
   —— 現在開いているのは `license-discuss` のスレッドであり、**この 6 は行っていない**
7. **（6 を行った場合の話）** **決定は「初回投稿から 60 日」ではない。** Licensing Committee の
   McCoy Smith 氏が 2026-08-28 に機構を説明している —— *"We work on a **two-month review cycle**"*
   で、起点は**最終提出**である（*"the July Board meeting was prior to two months from your final
   submission"*）。委員会が**理事会へ勧告**し、**理事会が会合で決める**（2026 年は 8 月に会合が無く
   9 月 24 日の対面会合へ回った）。**つまり本文を改訂するたびに時計が戻る** —— 凍結（§2）は
   礼儀ではなく、決定までの時間を最短にする手段でもある。
   `license-discuss` は議論の場なので決定という概念自体が無く、この期限は当てはまらない
