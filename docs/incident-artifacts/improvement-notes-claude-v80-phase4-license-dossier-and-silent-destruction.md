# ライセンス・ドシエと「利用者の操作を起点としない破壊」run

## この run を貫くもの

2 本ある。**(1) 提出中のライセンスについて、リポジトリを見れば疑問が全部潰せる状態を作る。**
**(2) 「利用者が何もしていないのに何かが失われ、しかも黙っている」面を潰す。**
後者は前半の「破壊的操作の確認文が何を失うかを言っていない」から自然に伸びた枝で、
**操作を起点とする破壊**（削除・上書き・全置換）を閉じ切ったあと、
**操作を起点としない破壊**（デプロイに伴う移行）へ移った。

## 1. ライセンス・ドシエ

`LICENSES/` に 14 ファイルの想定問答体系を置いた（索引 / 逐条リファレンス 82 条 /
既存ライセンスとの比較 / 法域別の地図 / 実務 FAQ / 議論ログ / 提出パケット）。

**投稿先の誤りを是正した。** 当初「OSI license-review へ提出済み」と 15 ファイルに書いていたが、
実際に出したのは **`license-discuss`（一般的な議論リスト）**であり、承認申請の窓口である
`license-review` でも SPDX 提出でもない。つまり**承認の手続きはまだ何も始まっていない**。
**Check 458 / 458b** で投稿先の記述を機械強制した。458b の初版は行単位の否定検出で、
同じ行にある無関係な否定が本物の誤りを打ち消して**非 vacuity 検証を素通り**した
（語の直後 40 文字以内・間に否定を挟まない、という近接判定へ直した）。

**起草主体の記述は 6 回の往復を経て確定した。** 最初は §4 A1 が "The drafting is my own" と述べ
Q10・§E.1 の「LLM が起草」と食い違っていた（**最も痛い場所＝先に自分から弱点を述べる節**にあった）。
そこから ①指示で起草 → ②**作る判断も人間発ではない**（AI が必要と判断して起草し、人間は存在を
後から知った）→ ③**申請の提案も別の AI 発** → ④**人間はリポジトリを見ていない** →
⑤**ただしライセンスは送付前に全文読了**、と 5 回追記・訂正した。

**教訓は「一方向に偏る」ではない。** 1〜5 は人間の関与を過大に、6 は過小に書いており向きは
一定していない。共通するのは**確かめずに書いた**ことだけである。書けるのは
**(a) 本人が述べたこと** と **(b) リポジトリに証跡があること** の 2 つで、どちらでもないなら
「した」とも「していない」とも書かない。6 回の往復は、この規律を持たずに書いた分だけ発生した。

**Check 459 / 460**: 到達できない文書は無いのと同じなので索引の網羅を強制。自称している件数
（条項数・分冊数・想定問答数）が実体と一致することを 4 面で強制。

**凍結は守った。** `ACD-1.0.txt` / `.spdx.xml` / `.machine.json` は Check 453 が sha256 を pin
しており、本 run では一切触れていない。

## 2. 予算統治 —— 早期警告が構造的に一度も鳴らない層

advisory 予算が hard ceiling（1,000 行）と同値以上だと Check 52 は一度も鳴らず、
**OK からいきなり BLOCKING へ飛ぶ**。実測で 6 ファイルがこの状態にあり、うち 1 つは
**BLOCKING まで 1 行なのに無警告**だった。**Check 443** で構造防止したが、
**初版は射程を絞らず正しい設定 3 件を誤検出した**（`style.css` / `index.html` / `main.js` は
ceiling 対象外ゆえ 1,000 超が正当）。除外集合を Check 365 と共有する単一ソースへ持ち上げた。

**advisory は上げて黙らせるのではなく、下げて早く鳴らす。** 本 run では advisory に 3 回当たり、
3 回とも BLOCKING を踏む前にテーマ分割で解消した（`checks_size_budget.py` の切り出し、
mutation ログの rotate、`apps-settings-snapshot.spec.js` の切り出し）。

**予算は上げる前に「削って収まるか」を実測する。** shipped byte は本 run で複数回ラチェットしたが、
毎回「WHY コメントを全部消したら収まるか」を測り、収まらない（＝超過は機能の分）ことを
確認してから上げ、その数字を予算ファイルに残した。

その 3 件に絞った根拠（「遅くなる」「中核が一致していれば検出できる」）は**実測で崩れた** ——

`index.html` 自身と機械可読層（**このリポジトリの中核の賭け**）も未検証だったので加えた
（**Check 457 / 457b / 457c**）。

## 4. 破壊的操作の確認文が「何を失うか」を言っていなかった

6 面を閉じた。とくに FatalPage の「保存データを削除して再読み込み」は **SNAPSHOT_KEY も削除する**
のに文言が言わず、**利用者の唯一の復元点が黙って消えていた**。全リセット側は逆に
「スナップショットは**残る**」と言う（残るものを伝えるほうが判断できる）。
スナップショットの**上書き**は削除と同じく不可逆なのに無確認、**全置換モード**は最も破壊的なのに
無確認だった。貼り付けで `maxLength` に切られた分も無反応だったので報告するようにした
（打鍵は「入らなくなる」のが見えるが、**貼り付けは無言で切られる**）。

## 5. 利用者の操作を起点としない破壊

**スキーマ版数が変わったデプロイで、利用者の全データが無言で既定へ戻っていた。**
実測（旧 `schemaVersion` を仕込んで開く）: タスク消失 / 可視トーストなし / SR 通知なし /
画面上の説明なし。旧データは `SNAPSHOT_KEY` へ退避されるので**救えるのに**、利用者からは
「開いたら全部消えていた」としか見えず復元導線に辿り着けない。
`store.load()` は描画前に走るので移行を記録するだけにし、`Toast` を注入済みの `state.js` が通知する。
文言は**消えたこと**と**復元できること**の両方を言う（片方だけでは、前者は不安にさせるだけ、
後者は何を復元するのか分からない）。

続けて、その復元先が**自分で保存したもの**か**移行時に自動退避されたもの**かを区別できない
ことが分かった。自動退避は描画前に走るため確認を挟めず、**手動保存を黙って上書きする**。
上書きを避ける選択肢もあるが、それは移行で捨てられる現在のデータを失わせるので採らない。
**消せない破壊性なら、せめて何が起きたかを見えるようにする。**

**「作らない」判断も記録した。** 読み込み時の正規化による切り捨ても同じく無言だが、実測すると
保存済みデータはその場では壊れず（520 件のまま）、そもそも**上限超過データを書き出す経路が
実装上存在しない**＝トリガが仮定だった。必要性を実測で示せないものは padding なので作らない。

## 6. 週次 probe が私のほころびを検出した（2 件）

(a) 前提が**データ条件**に依存する mutation が、対象ファイルの分割で silent に vacuous 化していた。
(b) export の形式を変えた結果、anchor しているテストがその分岐を通らなくなり test-anchor が鈍った。

「一意か」を見るのであって「**正しい対象を実際に打っているか**」は見ない。**probe だけが捕まえる。**

- checkbox を外すループが**再描画で外れていなかった**。

- probe の e2e mutation を **consistency 側の archive** で数え、「実証済み 46 件」と誤報告した
  （正しくは 357 / 418）。
- **CI のキュー遅延を「トリガ取りこぼし」と誤診しかけた** —— 2 PR 連続で BLOCKING gate が起動せず、
  close→reopen も効かなかったが、**ローカルで gate の中身を完走**（behavior e2e 487 件全緑）させて
  待ったところ、遅れて run が生成され全緑になった。**緑と偽って merge しない**ことだけは守った。
