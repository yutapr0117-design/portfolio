# LICENSES/README.md

## What

`LICENSES/` の**入口となる索引**。3 つの切り口で並べる。

1. **目的別**（「知りたいこと → 見る場所」の 12 行）
2. **立場別の読み順**（使うか決めたい人 / レビューする人・批判したい人 / 監査する人）
3. **いまの状態**（venue は `FROZEN.md` の単一ソースを参照し、**ここには直書きしない**）

## Why

このディレクトリは 14 ファイルまで増えた。**入口が無ければ、増やすほど見つからなくなる。** オーナーの目標は「**疑問が全てリポジトリを見たら潰せる**」であり、答えが存在することと**辿り着けること**は別である。

実測（2026-08-27）では orphan（どこからも参照されない文書）は 0 件だったが、**入口が存在しないため、将来 orphan が生まれても誰も気付けない**状態だった。

## How

- **状態を直書きしない。** venue は `FROZEN.md` の `VENUE-DATA` marker が単一ソースで、Check 458 が複数ファイルとの整合を強制する。README に書けば必ず drift する（実際 2026-08-26 の 1 日で venue の記録が 2 度 drift した）。
- **立場別の読み順**を置いたのは、同じ索引でも「使う人」と「批判したい人」では最初に読むべきものが違うため。批判したい人には **§4「認める項目」と「残る弱点」を先に**示している。
- 相対リンクで書き、`docs/architecture/acd-license-rationale.md` だけはディレクトリ外なので `../` で指す。

## 横断整合の監査（2026-08-27・方法と結果）

オーナー依頼「**起草主体と件数を含む残存矛盾を洗い出して整合させる**」に対して行った監査。**方法は再実行できる**ので手順を残す。

### 手順

1. **起草主体**: `drafting|起草|LLM|large language model` を文書群と rationale に当て、**主語が食い違う記述**を探す。
2. **件数**: `\d+ (条|節|問|件|項目|entries|clauses)` を全部拾い、**検証可能なものだけ**実測と突き合わせる（本文由来か corpus 由来かを分ける）。
3. **分冊数・ファイル数**: 「N 分冊」「across N files」型の主張を実数と照合する。

### 結果

| 面 | 結果 |
|---|---|
| **起草主体** | **矛盾 1 件**。§4 A1 が "The drafting is my own" と述べ、Q10・§E.1 の「LLM が起草」と食い違っていた → 是正済み。**最も痛い場所（先に自分から述べる節）にあった** |
| **件数（corpus 由来）** | **drift 4 件**（索引 / FAQ mirror / clause-reference mirror / README mirror）→ 是正し **Check 460** で機械強制 |
| **件数（本文由来）** | **clean**。597 行 / 16 節 / 82 条 / 定義語 10 / 相互参照 82 / 唯一の外部引用 / 凍結 3 件 —— いずれも実測と一致。**本文が凍結中である限り動かない**（Check 441b/441c/452/453 が個別に守る） |
| **分冊数** | **clean**。"across three files" は想定問答 3 分冊を指しており正確 |

### 次に走らせるとき

**本文由来の数は 1.1 以降でしか動かない**ので、平時に見るべきは **corpus 由来**（entry 数・行数・分冊数）である。そこは Check 460 が 4 面を押さえたので、**手動監査が要るのは Check がまだ見ていない面だけ**になった。

## Constraints

- **非規範。** 権威は `ACD-1.0.txt` のみ。
- **Check 459 (BLOCKING)** が「`LICENSES/*.md` がすべてここに現れる」ことを機械強制する。新しい文書を足して索引に載せ忘れると CI が止まる。
- 本書を根拠に `ACD-1.0.txt` を編集してはならない（Check 453）。

## Change impact

- **文書を足したら、この表にも行を足す**（足さないと Check 459 が RED）。
- 逆に「載っているのに答えが無い疑問」が出たら、それは**文書側の欠落**である。該当文書へ追記する。
- `ACD-1.0.faq.md` §C にも同種の逆引き表がある。**片方だけ更新すると drift する**ので、両方を見ること（現状は Check で縛っていない ―― 縛るなら「両表の行集合の一致」になるが、粒度と観点が違うため機械化すると誤検出しやすいと判断した）。

## Audience-specific notes

### For AI agents（次担当）

- 役割タグ: `license`, `index`, `entry-point`, `reachability`
- **状態（venue・進捗）をここに書かないこと。** 単一ソースは `FROZEN.md`。
- 文書を足したときは (1) この表、(2) `docs/files/` mirror、(3) 必要なら `faq.md` §C ―― の 3 面を同期する。(1) は Check 459 が、(2) は Check 108 が強制する。(3) は人の判断。

### For human engineers（新卒レベル）

資料が増えると「どこに何があるか」が分からなくなる。この README はその地図で、**立場ごとに最初に読むものを変えてある**。批判したい人には、弱点を先に見せる順序にしてある ―― 隠していると思われるほうが損だから。

### For third parties / auditors

監査向けの読み順を §2 に明示してある（凍結の sha256 → 提出判断と残る弱点 → 各文書の「扱っていないもの / 限界」の節）。**各文書が「何を扱っていないか」を自分から書いている**ことが、この文書群の設計方針である。
