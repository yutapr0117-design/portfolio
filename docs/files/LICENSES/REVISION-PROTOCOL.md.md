# LICENSES/REVISION-PROTOCOL.md

## What

OSI 承認までを**複数ラウンドの長期戦**として回すための手順書。1 ラウンドの流れ（受領 →
分解 → 分類 → 応答 → 改訂 → 再提出）、版管理の決定（**1.0 は永久凍結・次版は併置**）、
再提出前の 9 ゲート、やってはいけないこと、を定める。

## Why

リポジトリは **1 回の提出**を前提に組まれていた。凍結（Check 453）も discussion-log も
「1 度きり」の形で、**2 ラウンド目に何が起きるかが決まっていなかった**。返信が届いてから
設計を考えると、最も判断を誤りやすい局面（手元に指摘があり、直したい圧力がかかっている）で
版管理を決めることになる。**先に決めておくのが目的**である。

とくに 2 つを固定した。**受領文の無改変保存**（我々の読みは誤りうるが、何と言われたかの記録は
誤ってはならない）と、**読まれたテキストを書き換えない**（議論の対象が下で動けば、その議論は
何についてのものでもなくなる）。後者は §16.4（改変版は `ACD-1.0` を名乗れない）が本文の側から
要求していることでもある。

## How

版に紐づく文書と紐づかない文書を表で分ける。`against.md` と `discussion-log.md` は**全ラウンド
通し**にする —— 版を変えるたびに不利な事実が短くなるなら、それは改善ではなく記録の消去だから。
解決した項目は行を残して status を動かす。

`FROZEN.md` の FREEZE-DATA は**行を足す**運用（置き換えない）。Check 453 が表を単一ソースに
するので、1.0 の 3 行を残したまま次版の 3 行が増える形で自然に動く。

## Constraints

- **ライセンス本文 3 件は凍結中**（Check 453）。本書は手順を定めるだけで本文に触れない。
- 受領文の保存先 `LICENSES/rounds/` は**まだ存在しない**。最初の返信が届いた時点で作り、
  同時に `docs/files` mirror（Check 108）と索引（Check 459）を足す。
- venue の記述は `FROZEN.md` の VENUE-DATA が単一ソース（Check 458）。

## Change impact

ラウンドが進むたびに §1 の表と §3 のゲートを実際に使う。手順を変えるときは、**なぜ変えたかを
discussion-log に残す** —— 手順の変更が指摘への反応なのか、こちらの都合なのかを後から
区別できるようにするため。

## Audience-specific notes

- **審査者**: §0 に英文で 2 つの約束（無改変保存・読まれたテキストを動かさない）を置いてある。
- **監査人**: 「まだ起きていないことの手順は書かない」（§5）を明示している。承認後の手順を
  先に書くと、起きていないことについての記録が残るため。
